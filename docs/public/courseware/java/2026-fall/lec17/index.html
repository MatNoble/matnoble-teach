机房实操 · 接收端

接收端：等两包，按实际长度解码

UdpGreetingReceiver.java 完整程序 · 26 行 
import java.net.DatagramPacket;
import java.net.DatagramSocket;
import java.net.InetSocketAddress;
import java.nio.charset.StandardCharsets;

public class UdpGreetingReceiver {
    public static void main(String[] args) throws Exception {
        int port = args.length == 0 ? 16017 : Integer.parseInt(args[0]);
        try (DatagramSocket socket = new DatagramSocket(
                new InetSocketAddress("127.0.0.1", port))) {
            socket.setSoTimeout(30_000);
            System.out.println("正在等待两个数据报，端口 " + port);

            byte[] buffer = new byte[64];
            for (int i = 1; i <= 2; i++) {
                // 可以复用数组，每次接收都用一个新的 packet 对象。
                DatagramPacket packet = new DatagramPacket(buffer, buffer.length);
                socket.receive(packet);
                int length = packet.getLength();
                String text = new String(packet.getData(), packet.getOffset(),
                        length, StandardCharsets.UTF_8);
                System.out.println("第 " + i + " 包：" + length + " 字节 | " + text);
            }
        }
    }
}
RECEIVER · 对照左边的序号
  1. ①

    绑定 127.0.0.1:16017。UDP 接收端不用等连接，绑好端口就能收。

  2. ②

    给 receive() 设 30 秒上限：等不到下一包就抛 SocketTimeoutException。

  3. ③

    停在这里等下一份数据报；到达后，这份数据就装在 packet 里。

  4. ④

    本包有效长度：10 或 2，由对方发来的内容决定，不是数组容量 64。

  5. ⑤

    从本包起点 getData()[getOffset()] 起、按 length 解码；数组其余格子不参与。

发送端：把每条文字装进一包

UdpGreetingSender.java 完整程序 · 22 行 
import java.net.DatagramPacket;
import java.net.DatagramSocket;
import java.net.InetAddress;
import java.nio.charset.StandardCharsets;

public class UdpGreetingSender {
    public static void main(String[] args) throws Exception {
        int port = args.length == 0 ? 16017 : Integer.parseInt(args[0]);
        InetAddress host = InetAddress.getByName("127.0.0.1");
        String[] messages = {"hello java", "ok"};
        try (DatagramSocket socket = new DatagramSocket()) {
            for (String text : messages) {
                // 每次 send 提交一份数据报，本例没有应用层回执。
                byte[] data = text.getBytes(StandardCharsets.UTF_8);
                DatagramPacket packet = new DatagramPacket(data, data.length, host, port);
                socket.send(packet);
                System.out.println("已发出：" + text);
            }
        }
    }
}
SENDER · 对照左边的序号
  1. ①

    两句要发的话，都不加换行——数据报的边界不靠它。

  2. ②

    把字节数组、长度和收件地址端口装进一封“明信片”。

  3. ③

    投出去就返回：UDP 不确认、不重发；两封寄完程序结束。

RECEIVER · 同一个 byte[64] buffer，两次接收后各是什么样？
第 1 包（length = 10）
68656C6C6F206A617661… 其余 54 格是旧数据
第 2 包（length = 2）
6F6B… 其余 62 格是旧数据
数组容量 64 是“最多装多少”；getLength() 才是“这包实际多少”。如果接收数组比数据报小，超出部分会被截掉——所以缓冲区要留够。重复使用同一个 DatagramPacket 接收时，长度每轮都会变。

概念 · 把名词说清楚

UDP 是什么：一封封独立寄送的明信片

定义

UDP（User Datagram Protocol，用户数据报协议）：规定两个程序如何以一封封独立的数据报收发消息的通信协议。DatagramSocket / DatagramPacket 是 Java 里使用它的入口。它也建在 IP 之上：IP 只管把一个个包尽力送到对方机器，UDP 再加上端口与长度，其余交给你。

UDP 保证
  • 保留每次 send() 的边界——一份数据报一次交付，长度各自为准。
  • 无需先建立连接：写上地址端口就能寄，没有握手。
  • 没有确认、重传的额外开销，轻量。
UDP 不管
  • 不保证送达、顺序，也不去重。
  • 不给发送端任何回执：丢了还是到了，发送端都不知道。
  • 数据报里每段字节的含义，仍由应用约定——任务二见。
TCP 像一通电话：先接通、边说边确认；UDP 像寄明信片：每张独立寄出，可能丢、可能迟到，邮局不给回执。第 16 讲的可靠由连接保证，这一讲的可靠要靠应用自己。

回看程序 · 对照两端

收发用 DatagramSocket，数据装进 DatagramPacket

接收端代码片段 · UdpGreetingReceiver.java

        new DatagramPacket(buffer, buffer.length);

构造时只给“装东西的盘子”：等 receive() 把一份数据报装进去。

发送端代码片段 · UdpGreetingSender.java

        data, data.length, host, port);

构造时还要写清内容和收件地址端口——明信片上那几行字。

对象谁使用负责什么打比方
DatagramSocket两端各一个绑定端口；send() 寄出、receive() 收下邮筒：寄件、收件都走它
DatagramPacket每次收发一份装着 byte[] 数据＋长度＋地址端口明信片：内容与收件地址写在一起
ServerSocket / Socket第 16 讲 · TCP先接通，再沿连接读写流电话：先拨通，再连续说话
同一个 DatagramSocket 既能收也能发；差别只在构造 packet 时写没写收件地址，以及调用 send 还是 receive。

从两个实验比较

什么时候选 TCP，什么时候考虑 UDP？

TCP · 需要有序、可靠的字节流

例如文件传输、登录、指令下发：少一个字节都不行。

应用仍要自己规定消息边界（第 18 讲）。

UDP · 独立报文，可容忍遗漏

例如周期性状态上报：较新的状态可以替代旧的，丢一帧，下一帧很快就来。

要确认、排序或去重时，由应用程序自己做。

选择看业务要求，不看“哪个更快”。本机两个实验都快，不能据此下结论。课程设计的设备遥测走 UDP：周期上报加心跳，正合适——丢了能靠下一条补，断了能靠心跳发现。

拆解程序 · 字段位置

先检查格式，再恢复三个坐标

写的一侧 · encode()

按帧表组装：表头四字节 → putFloat() 写三个坐标 → 电量 → 按索引 2–17 算出校验 → 最后写校验字节和帧尾。

先放内容、后补校验：因为校验覆盖的是已经放好的字节。

读的一侧 · inspect()
ByteBuffer in = ByteBuffer.wrap(frame)
        .order(ByteOrder.BIG_ENDIAN);
in.position(5);
float x = in.getFloat();

确认总长、固定字段和校验值之后，才从第 5 格开始读。

这里的 position(5) 把读取起点从第 15 讲的数组开头，移到本帧的载荷。顺序不能反：先检查长度和格式，再访问固定索引——总长不是 21，就谈不上“索引 17 是电量”。

拼装与检查一条帧：TelemetryFrameLab

TelemetryFrameLab.java 完整程序 · 105 行 · 可滚动 
import java.net.DatagramPacket;
import java.net.DatagramSocket;
import java.net.InetAddress;
import java.net.InetSocketAddress;
import java.nio.ByteBuffer;
import java.nio.ByteOrder;
import java.util.Arrays;
import java.util.HexFormat;

public class TelemetryFrameLab {
    public static void main(String[] args) throws Exception {
        byte[] frame = encode(1, 1.5f, -2.0f, 0.5f, 87);
        if (args.length > 0 && args[0].equals("udp")) {
            frame = sendAndReceive(frame);
            System.out.println("UDP 收到：" + frame.length + " 字节");
        }
        String hex = HexFormat.ofDelimiter(" ").withUpperCase()
                .formatHex(frame);
        System.out.println("原帧：" + hex);
        inspect(frame);

        byte[] changed = frame.clone();
        changed[17] = 86; // 模拟数据变化，保留原校验字节。
        System.out.print("只改电量：");
        inspect(changed);

        changed[2] = 2; // 编号 +1，抵消电量 -1。
        System.out.print("再改编号：");
        inspect(changed);
        System.out.printf("CRC-16 对照：%04X → %04X%n",
                crc16(frame), crc16(changed));
    }

    static byte[] sendAndReceive(byte[] frame) throws Exception {
        InetAddress loopback = InetAddress.getByName("127.0.0.1");
        // 接收端已经绑定，发送后再取出排队的数据报。
        try (DatagramSocket receiver = new DatagramSocket(
                     new InetSocketAddress(loopback, 0));
             DatagramSocket sender = new DatagramSocket()) {
            receiver.setSoTimeout(3_000);
            sender.send(new DatagramPacket(frame, frame.length,
                    loopback, receiver.getLocalPort()));
            byte[] buffer = new byte[64];
            DatagramPacket packet = new DatagramPacket(buffer, buffer.length);
            receiver.receive(packet);
            return Arrays.copyOfRange(buffer, packet.getOffset(),
                    packet.getOffset() + packet.getLength());
        }
    }

    static byte[] encode(int id, float x, float y, float z, int battery) {
        ByteBuffer out = ByteBuffer.allocate(21).order(ByteOrder.BIG_ENDIAN);
        out.put((byte) 0xEB).put((byte) 0x90);
        out.put((byte) id).put((byte) 1).put((byte) 13);
        out.putFloat(x).putFloat(y).putFloat(z).put((byte) battery);
        byte[] frame = out.array();
        out.put((byte) checksum(frame)).put((byte) 0x0D).put((byte) 0x0A);
        return frame;
    }

    static void inspect(byte[] frame) {
        // 先检查长度，才能安全地检查固定索引。
        if (frame.length != 21 || (frame[0] & 0xFF) != 0xEB
                || (frame[1] & 0xFF) != 0x90
                || frame[19] != 0x0D || frame[20] != 0x0A
                || frame[3] != 1 || frame[4] != 13) {
            System.out.println("拒绝：帧格式错误");
            return;
        }
        if ((frame[18] & 0xFF) != checksum(frame)) {
            System.out.println("拒绝：累加和不匹配");
            return;
        }
        // 第 15 讲的坐标读取方式，起点改为载荷索引 5。
        ByteBuffer in = ByteBuffer.wrap(frame).order(ByteOrder.BIG_ENDIAN);
        in.position(5);
        float x = in.getFloat();
        float y = in.getFloat();
        float z = in.getFloat();
        int battery = in.get() & 0xFF;
        System.out.printf("设备 %d，坐标 (%s, %s, %s) m，电量 %d%%%n",
                frame[2] & 0xFF, x, y, z, battery);
    }

    static int checksum(byte[] frame) {
        int sum = 0;
        for (int i = 2; i < 18; i++) {
            sum += frame[i] & 0xFF;
        }
        return sum & 0xFF;
    }

    // CRC-16/CCITT-FALSE，保护同一段数据。
    static int crc16(byte[] frame) {
        int crc = 0xFFFF;
        for (int i = 2; i < 18; i++) {
            crc ^= (frame[i] & 0xFF) << 8;
            for (int bit = 0; bit < 8; bit++) {
                int polynomial = (crc & 0x8000) == 0 ? 0 : 0x1021;
                crc = ((crc << 1) ^ polynomial) & 0xFFFF;
            }
        }
        return crc;
    }
}
对照左边的序号
  1. ①

    生成原帧：设备 1，坐标 (1.5, -2.0, 0.5)，电量 87。

  2. ②

    encode()：按帧表组装 21 字节，最后回填校验与帧尾。

  3. ③

    sendAndReceive()：带 udp 参数时才调用，第 26–27 页展开。

  4. ④

    inspect() 第一步：长度或固定字段不对，直接拒绝。

  5. ⑤

    第二步：重算索引 2–17 的和，与第 18 字节比对。

  6. ⑥

    checksum()：无符号加总，只留低 8 位。

  7. ⑦

    crc16()：CRC-16 对照，不是本帧的校验字段。

检错 · 累加和

只改电量，原来的校验字节还对吗？

怎么计算

把索引 2–17 的字节按无符号数加起来：1+1+13+63+192+…+87＝612＝0x264，只留低 8 位 → 0x64，写进索引 18。

改动任何一个被覆盖的字节，和几乎都会变。

先预测

只把电量从 87 改成 86，旧的校验字节 64 还匹配吗？

如果同时把设备号从 1 改成 2 呢？

核对结果

只改电量：和变 0x63 ≠ 0x64，拒绝。设备号 +1 与电量 −1 相抵：和回到 0x64，通过——同一帧里的两处改动，累加和只看总量。

接收端不能因为“校验通过”就相信每个字节都没被动过——这个盲区，下一页拆开看。

检错 · 从总量到位序列

一加一减骗过累加和，为什么骗不过 CRC？

累加和看的是总量

不同位置的字节一加一减可以相抵；字节挪位也可能凑出同一个和。

CRC 按顺序处理每一位

把字节串当作多项式，用约定的生成多项式做模 2 除法（异或当减法）。位置和顺序都影响余数——同样的一加一减，余数不同。

代码里的 CRC-16/CCITT-FALSE（初值 FFFF、多项式 1021、覆盖索引 2–17）只作对照，本帧真正用的是 1 字节累加和。若协议改用 CRC-16，双方必须统一参数、覆盖范围和字段长度；CRC 也仍可能漏检，只是难得多。上图的数值都来自左边程序的真实运行。

看清演示的边界

同一进程里的两个套接字

sendAndReceive() 做了什么
  1. receiver 绑定 127.0.0.1:0——端口填 0，由系统挑一个空闲的。
  2. sender 向 receiver.getLocalPort() 寄出这 21 字节。
  3. receiver.receive() 取出排队的数据报，按 getLength() 截取有效部分返回。
它演示了什么、没演示什么

演示：一条帧可以完整装进数据报、原样取出，再通过同一套检查。

没演示：两台机器和真实网络——同一进程里两步就到，不会丢包。

真实的两端，就是第 7、8 页那样的两个独立程序。课程设计里，模拟设备和主机也是这样两个进程——中间才是真正的网络路径，丢包、延迟都从那里来。

今天的约定

一个数据报恰好承载一条 21 字节帧；字段的位置和含义由帧表约定，接收端按表检查、再解析。

下一讲 · 同一条帧进入 TCP 字节流

一次 read() 可能只读到半帧，也可能一次读到连在一起的两帧。接收端要先找到边界——固定长度、分隔符、长度字段或状态机——再交给本讲的解析方法。

UDP 的边界到数据报为止。TCP 的字节流里没有数据报，边界全靠应用自己找——这是第 18 讲的主线。
